# 0001. Stack and architecture for the PDF tool site

**Date**: 2026-10-10
**Status**: In Progress

## Summary

This picks the base technology for the site before any code exists. The site is built as static HTML pages (pages rendered to plain HTML at build time, which is what search engines read best), generated by Astro, with a small piece of interactive code on each tool page. All PDF work (merge, split, compress) runs in the visitor's own browser, inside a Web Worker (a background thread that keeps the page responsive), so files never leave the device. The site lives on Cloudflare, which serves static pages cheaply and can run the one server job later, the PDF to Word converter. Every later feature builds on this base.

## Decision

**Chosen option**: Option 1: Astro static site, client side PDF engine, Cloudflare Pages.

The site is a static Astro project (TypeScript throughout), with Tailwind CSS for styling, pdf-lib plus PDF.js running in Web Workers for all client side PDF work, and Cloudflare Pages as the host, including a reserved server area for the converter and API later.

**Implementation skills**: none. No community skill for this stack was found in the registry check (searched: Astro, pdf-lib, pdfjs-dist, Tailwind, Cloudflare, Vitest, Playwright); the workflow skills (develop, check, test) cover the process.

RECOMMEND calls settled here (pick, one line why, runner up):

- **Rendering mode**: Astro static output with per island hydration (only tool islands load client code). Runner up: Astro server rendering, unneeded since nothing is personalized yet.
- **PDF library loading**: pdf-lib and PDF.js are loaded only inside the Web Worker via dynamic import, so landing and variant pages never download them. Runner up: bundling them globally, rejected because it would bloat every content page.
- **Deployment wiring**: Cloudflare Pages connected to the git repository, so each push builds and gets a preview URL. Runner up: manual wrangler CLI deploys from a script.
- **Server area shape**: a `functions/` directory (Cloudflare Pages Functions, one file per route under `/api`), adopted in earnest at the converter release. Runner up: a separate Worker service, rejected as extra infrastructure for one tool.
- **Security headers**: set baseline headers (content security policy that allows worker and blob scripts, clickjacking protection, no referrer leaks) in the Pages configuration during the scaffold. Runner up: deferring entirely, rejected because retrofitting headers later risks breaking the tools.
- **Runtime pinning**: pin a Node LTS version in `package.json` engines plus a version file, so builds behave the same over the years. Runner up: leaving it floating.
- **Compression honesty**: the compress presets disclose that smaller files come from re compressing and downsampling images (a quality tradeoff), and show the real before and after size. Runner up: promising lossless shrinking, which client side cannot reliably deliver.
- **International readiness**: the content collections (Astro's folder of structured content files) are keyed so a future locale can be added without a rewrite; the data model spec owns the details. Runner up: ignoring it, which makes the later translation work a migration.

## Proposed stack

| Layer | Choice | Reason |
|---|---|---|
| Language | TypeScript (strict mode) | pdf-lib and PDF.js are loosely typed libraries; types catch API misuse early on a project built release by release. |
| Framework | Astro, static output, islands per tool | Pure HTML pages for search engines, client code only where a tool needs it. |
| UI styling | Tailwind CSS | Fast, consistent styling now; the design system feature layers tokens on top of it. |
| PDF engine | pdf-lib (structure: merge, split, reorder) + PDF.js (rendering, thumbnails, lossy compression), both in Web Workers | Covers all client side tools while keeping the page responsive on large files and phones. |
| Primary database | None | The foundation is stateless; nothing to store. The API release can add Cloudflare D1 (SQLite at the edge) if rate limiting needs persistence. |
| Auth | None | No accounts in scope; revisit only if a premium tier appears. |
| Background jobs | None | All processing happens in the visitor's browser. |
| File storage | None | Files stay in browser memory; the converter at Release 5 uses short lived uploads, decided in its own spec. |
| Hosting | Cloudflare Pages (static) + Pages Functions (the `/api` area) | Free unlimited static requests, commercial use allowed, and the one server tool fits the same deployment. |
| Observability | Cloudflare request logs now; analytics, consent, and error tracking decided at Release 4 | Keeps the foundation lean while the consent feature owns the honest minimum. |
| Testing | Vitest (unit, PDF helpers) + Playwright (one browser flow per tool release) | Catches in browser regressions that unit tests alone miss. |
| Package manager | pnpm, single application | Fast, strict installs; no monorepo overhead until a second deployable exists. |

### Scaffold shape

The scaffold (the feature 1 build) should land roughly like this. Names may shift during implementation, the structure should not:

```
src/
  pages/            one route per landing page and tool
  components/       UI islands, plus shared metadata and JSON-LD components
  layouts/          page chrome
  content/          content collections: tools now, variant page definitions later
  lib/pdf/          typed wrappers around pdf-lib and PDF.js
  workers/          Web Worker entry points: merge, split, compress
functions/          Pages Functions: /api routes (empty shell now, converter at Release 5)
public/             static assets, generated sitemap
tests/              Vitest unit tests
e2e/                Playwright flows
```

Conventions the scaffold establishes: tool islands hydrate with `client:load`, PDF libraries are imported only inside workers, every page carries its own title, description, canonical URL, and JSON-LD from the shared components, and the sitemap is generated at build time from the route list.

### Build conventions

**Environment and site URL**: one build constant, `SITE_URL`, is the source of every absolute URL (canonical tags, sitemap entries, social cards). Production builds use the production domain. Preview builds use their own preview URL, and previews are excluded from the sitemap and carry no canonical claim on the production domain. One canonical form is used everywhere: no trailing slash except the site root.

**Versions and pinning**: exact dependency versions are pinned in `package.json`, the pnpm lockfile is committed, and Node LTS is pinned in `engines` plus a version file. The Tailwind major version (v4 or v3) follows the browser support matrix below, not the other way around.

**Browser support**: the last two versions of Chrome, Firefox, Safari, Edge, and iOS Safari. Tool pages in a browser without Web Worker support show a clear "not supported" message instead of silently running heavy work on the main thread.

**Worker message contract**: one typed message set defined in the scaffold and reused by every tool: `progress` (percent or pages done), `result`, `error`, and `cancel`, with the worker answering a cancel message promptly. This is the single contract, not a per tool invention.

**Performance budget**: landing and variant pages ship under 50 KB of JavaScript (measured gzipped) on first load. The PDF libraries load only on tool pages, only inside the worker.

**Header check**: the production build is smoke tested against the real response headers, with an explicit worker source rule in the content security policy rather than a blanket allowance.

### Scaffold done criteria

Feature 1 is done when: `pnpm dev` serves the site locally, `pnpm build` produces the static output plus the `functions/` shell, `pnpm test` and `pnpm build` both pass in CI, and the built site loads under the production headers with its worker scripts running. That is the meaning of "boots locally and passes build" in the scope.

## Consequences

**Positive**:
- The growth engine gets the strongest possible foundation: static HTML, fast first paint, metadata generated at build time.
- The core promise holds by architecture, not by discipline: files never leave the browser, because the processing code runs there.
- Hosting costs stay near zero while traffic is small, and the plan allows commercial use, which an ads funded site requires.
- The one server tool later slots into the same deployment rather than a second system.

**Negative / tradeoffs**:
- Client side compression is honest but limited: text heavy PDFs shrink little, and big savings on image heavy files cost quality. Presets must manage expectations.
- The Web Worker wiring costs extra work in the first tool compared with running on the main thread.
- pdf-lib's release cadence has slowed (v1.17.1 was the latest at the time of the check), so pinning alone is not enough: the project should be ready to patch if maintenance stalls.
- Web Workers protect responsiveness, not capacity: a large PDF can still exhaust memory on a low end phone, so every tool needs its own size and page limits (set in each tool's spec).
- Cloudflare's execution limits apply to the converter when it arrives: Pages Functions inherit Worker CPU, memory, and request body limits, so long conversions on big files need validated limits or a different route for that release.
- Astro's island model and content collections are specific ways of working; a future contributor must learn them.

**Neutral**:
- TypeScript strict mode, Tailwind, Vitest, and Playwright become the conventions every later feature inherits.
- No database and no auth means nothing to migrate for a long while; when the API arrives, rate limit storage can come from D1 without changing this shape.
- The pdf-lib engine is reusable by that future API, since it runs in any JavaScript runtime.
